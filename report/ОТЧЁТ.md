# ОТЧЁТ
## Лабораторная работа: «Геоинтеллектуальный веб-сервис анализа городской инфраструктуры»

**Стек:** Leaflet.js 1.9 (локально) + OSM через `/api/tiles` · Express (Node.js) · YandexGPT API (yandexgpt-lite)
**Интерфейс:** тёмная стеклянная тема, вдохновлённая Google Antigravity (фиолетово-синие градиенты, orb-фон, агентская панель)
**Город:** Якутск, Республика Саха (Якутия) (центральная часть города)

---

## 1. Цель и решаемая задача

Разработано интерактивное веб-приложение, объединяющее картографическую визуализацию
(Leaflet + OpenStreetMap) и большую языковую модель (YandexGPT) для анализа пространственных данных.

Пользователь кликает объект на карте (школа, поликлиника, парк, остановка), задаёт вопрос
на естественном языке («Сколько школ в радиусе 1 км от выбранной остановки?») и получает
ответ ИИ, сформированный на основе переданных ему координат и атрибутов объектов.

## 2. Архитектура

Подробная схема: **`report/architecture.svg`**

```
┌────────────────────┐    POST /api/ask     ┌─────────────────────┐    HTTPS + Api-Key    ┌──────────────────────┐
│  Браузер (клиент)  │ ───────────────────▶ │  Прокси (Express)   │ ────────────────────▶ │  YandexGPT API       │
│                    │   {question,         │  :3000              │   completion request  │  llm.api.cloud.      │
│  Leaflet + OSM     │    objects,          │                     │                       │  yandex.net          │
│  26 объектов       │    selectedObject,   │  • валидация        │                       │  yandexgpt-lite      │
│  popup, фильтры,   │    mapCenter}        │  • сборка промпта   │ ◀──────────────────── │                      │
│  подсветка         │ ◀─────────────────── │  • демо-анализатор  │   answer + OBJECTS    │                      │
│                    │   {answer,           │  • обработка ошибок │                       └──────────────────────┘
└────────────────────┘    mentionedIds, ...}└─────────────────────┘
         │  GET /api/objects (data.json)         │  .env: YC_API_KEY / YC_OAUTH_TOKEN — токены НЕ покидают сервер
         ▼
   data/data.json (26 реальных объектов из OpenStreetMap)
```

**Обоснование прокси.** Прямой запрос из браузера к YandexGPT невозможен технически
(CORS) и опасен: API-ключ был бы виден любому пользователю в DevTools → вывод средств,
масштабирование под чужим именем. Express-прокси хранит ключи в `.env` на сервере
и возвращает клиенту только готовый текст ответа.

## 4. Реализация функциональности (этапы 2–4)

### Карта
- Leaflet 1.9.4 (локально в `public/vendor/`) + тайлы OpenStreetMap через локальный
  прокси `/api/tiles` (без API-ключа), затемнённые CSS-фильтром под тёмную тему;
  центр — Якутск, `fitBounds` по объектам.
- Интерфейс: тёмная «космическая» тема в стиле Google Antigravity — стеклянные панели,
  градиентный акцент, орбы на фоне, тёмные контролы Leaflet и светящиеся маркеры.
- Маркеры — `L.divIcon`: цветная «капля» + эмодзи типа, легенда в углу карты.
- Popup: название, тип, адрес, описание, подсказка про выбор объекта.
- Фильтры: чекбоксы по 5 типам (`renderMarkers()` перерисовывает слой).

### Взаимодействие «выбор → вопрос → ответ»
1. Клик по маркеру → объект фиксируется как `selectedObject` (синяя подсветка + чип
   в панели ИИ).
2. В поле ввода пишется вопрос; Enter или кнопка «Спросить».
3. Фронтенд формирует контекст (см. §5) и отправляет `POST /api/ask`.
4. Прокси собирает промпт, вызывает YandexGPT (или демо-анализатор), возвращает
   `{ answer, provider, mentionedIds, circle }`.
5. Ответ выводится в чат; упомянутые объекты подсвечиваются фиолетовым пульсирующим
   маркером + строится круг радиуса анализа.

### Демо-анализатор
Если ключи Yandex Cloud не заданы, сервер автоматически включает локальный
«ИИ на правилах»: распознаёт тип объекта и радиус в тексте вопроса, считает расстояния
по формуле гаверсинуса, формирует ответ со списком объектов и расстояниями.
Это позволило протестировать всю цепочку до подключения ключей.

## 5. Формирование контекста для ИИ

Ключевой фрагмент — функция `buildContext()` в `public/js/app.js`:

```js
function buildContext() {
  let candidates = allObjects.filter((o) => activeFilter.has(o.type));

  const center = selectedObject || { lat: map.getCenter().lat, lng: map.getCenter().lng };

  // объекты видимой области (при выборе объекта — с запасом 1.5)
  if (selectedObject) {
    const b = map.getBounds().pad(1.5);
    candidates = candidates.filter((o) => o.id === selectedObject.id || b.contains([o.lat, o.lng]));
  } else {
    const b = map.getBounds();
    candidates = candidates.filter((o) => b.contains([o.lat, o.lng]));
  }

  // сортировка по удалённости от точки отсчёта (гаверсинус) и ограничение длины
  if (candidates.length > CONTEXT_LIMIT /* 25 */) {
    candidates = candidates.slice().sort((a, b) => dist(a) - dist(b)).slice(0, CONTEXT_LIMIT);
  }

  // компактная сериализация: только значимые поля
  const objects = candidates.map((o) => ({
    id: o.id, name: o.name, type: o.type, address: o.address,
    lat: +Number(o.lat).toFixed(6), lng: +Number(o.lng).toFixed(6),
    description: o.description || undefined,
  }));

  const mapCenter = { lat: +map.getCenter().lat.toFixed(5), lng: +map.getCenter().lng.toFixed(5) };
  return { objects, mapCenter };
}
```

Ограничения контекста учтены так:
- в промпт идут **только объекты видимой области** карты (или окрестности выбранного);
- максимум **25 объектов** (`MAX_OBJECTS_IN_CONTEXT`), отсортированных по близости;
- координаты округляются до 6 знаков, пустые поля отбрасываются;
- `maxTokens: 500` в `completionOptions`, а сервер отклоняет запросы с контекстом
  длиннее лимита (HTTP 413);
- системный промпт требует отвечать только по данным («если ответа нет в данных —
  скажи об этом») и добавлять служебную строку `OBJECTS: [id…]` для подсветки.

## 6. Обработка ошибок (этап 5)

| Сценарий | Как обработано |
|---|---|
| Пустой вопрос | Валидация на клиенте (`if (!question) …`), на сервере HTTP 400 |
| Неверный/просроченный токен | Прокси различает 401/403 Yandex Cloud → понятное сообщение «токен недействителен или просрочен, IAM живёт 12 часов», статус 401 |
| Превышение лимита запросов | 429 → «Превышен лимит запросов, подождите» |
| Слишком большой контекст | Лимит 25 объектов + HTTP 413 от сервера |
| Таймаут | `AbortController` на сервере (30 с) и клиенте (40 с) → сообщение «превышено время ожидания» |
| Сеть/сервер недоступен | `fetch` catch → сообщение в чат и статус-бар |

## 9. Ответы на контрольные вопросы

**1. Почему запрос к YandexGPT API нельзя выполнять напрямую из браузера?**

Три причины. (а) **Безопасность**: для вызова API нужен секретный ключ/IAM-токен; в браузере
любой код и любой перехват запроса видны пользователю (DevTools → Network). Утекший ключ
позволяет тратить чужую квоту и деньги, подделывать запросы от имени владельца. (б)
**CORS**: серверы Yandex Cloud не отдают заголовки `Access-Control-Allow-Origin`, поэтому
браузер просто заблокирует cross-origin запрос (curl/сервер — нет, браузер — да). (в)
**Контроль и лимиты**: прокси позволяет валидировать запросы, ограничивать частоту
(rate limit) и объём контекста до передачи в платный API. Поэтому ключ живёт в `.env`
на сервере, а браузер общается только со «своим» прокси.

**2. Как формируется контекст и какие ограничения учитывались?**

Контекст = системный промпт (роль ГИС-ассистента, правило «только по данным») +
вопрос + JSON выбранного объекта (если есть) + центр видимой области + компактный JSON
объектов (id, name, type, address, lat, lng, description). Ограничения контекста у
LLM конечны (для yandexgpt-lite — порядка 8k токенов промпта, ответ ограничен
`maxTokens: 500`); чтобы не превышать лимит, я передаю только объекты видимой области
карты, не более 25, отсортированных по удалённости от выбранного объекта/центра,
координаты округляю до 6 знаков и отбрасываю пустые поля. Сервер дополнительно
защищается лимитом (`MAX_OBJECTS_IN_CONTEXT`) и возвращает 413 при превышении.

**3. Как автоматизировать обновление IAM-токена?**

IAM-токен живёт 12 часов. Способы: (а) **OAuth-токен + обмен** — реализовано в работе:
прокси хранит долгоживущий `YC_OAUTH_TOKEN` и сам вызывает
`POST https://iam.api.cloud.yandex.net/iam/v1/tokens` (`{yandexPassportOauthToken}`),
кэширует IAM-токен и обновляет его за 5 минут до истечения `expiresAt`; (б) в продакшене
правильнее **сервисный аккаунт + API-ключ** (без expiry, как в этой работе) либо
**виртуальная машина / serverless с привязкой сервисного аккаунта**: тогда IAM-токен
получается через **metadata-сервис** (`http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token`)
без всяких секретов — Yandex Cloud сам выдаёт короткоживущий токен с авто-refresh;
(в) для CI/батчей — `yc iam create-token` из CLI с авторизацией ключом сервисного
аккаунта (JWT-подпись, `getIamToken`). Дополнительно ставится задача по cron/таймеру
на обновление кэша.

**4. GeoJSON vs тайлы (в т.ч. векторные Mapbox)?**

GeoJSON — это **данные целиком** в явной, читаемой форме: каждый объект — запись
с координатами и атрибутами; идеален для небольших наборов (сотни–тысячи точек),
когда нужен полный клиентский анализ: фильтрация, popup, выбор объекта, передача
атрибутов в LLM, измерения. Тайлы — **предрасчитанная пирамидальная нарезка для
рендеринга**:
данные нарезаны по клеткам (XYZ) и уровням масштаба, браузер грузит только видимую
часть; векторные тайлы (MVT/PBF, Mapbox/MapLibre) хранят геометрию компактно
(бинарная кодировка), raster-тайлы — уже готовые картинки. Тайлы предпочтительны при
больших объёмах (город, страна, миллионы объектов), когда нужна скорость и масштаб;
GeoJSON — когда нужна семантика и интерактивная работа с каждым объектом, как в этой
лабораторной (20 точек). Гибрид: векторные тайлы для отображения + GeoJSON поверх для
интерактивного слоя.

**5. (Повышенная сложность) Алгоритм автоматической подсветки объектов, упомянутых ИИ.**

Реализовано в работе. Алгоритм:
1. В системный промпт добавляется требование: «если упоминаешь объекты, в конце ответа
   добавь строку `OBJECTS: [id1,id2,…]` по их id из контекста» (структурированный канал
   поверх естественного текста — надёжнее, чем парсить имена).
2. Сервер после получения ответа извлекает эту строку регэкспом
   `/OBJECTS\s*:\s*\[([^\]]*)\]/i`, парсит список id, удаляет служебную строку из
   текста ответа и возвращает клиенту `mentionedIds`.
3. Фронтенд для каждого id ищет маркер в `Map<id, L.Marker>` и меняет иконку
   (`setIcon`) на вариант `mentioned` (фиолетовая обводка + CSS-анимация пульса),
   рисует `L.circle` радиуса анализа и подлетает к первому упомянутому объекту.
   Перед новым вопросом подсветка снимается (`clearHighlight`).
4. Fallback на неточных id: нестрогое сравнение имени из ответа с объектами контекста
   (нормализация регистра/кавычек), а в перспективе — structured output /
   function calling, чтобы модель возвращала `mentioned: [id]` как поле JSON-схемы,
   что исключает парсинг текста вовсе.

## 10. Выводы

- Реализована полная цепочка «данные → карта → выбор объекта → контекст → LLM → ответ →
  визуальная обратная связь на карте».
- Прокси-сервер решает задачи безопасности ключей, валидации, лимитов и обработки ошибок.
- Продемонстрировано, что LLM эффективно работает «интеллектуальной надстройкой» над
  ГИС-данными: отвечает по фактам, считает расстояния по координатам, а служебный канал
  `OBJECTS:` замыкает ответ модели обратно на карту.
